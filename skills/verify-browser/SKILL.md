# verify-browser — ブラウザ実機検証（合格判定 + 自律ループ）

画面を描画・操作・調査し、合格基準を満たすまで「検証 → 原因特定 → 修正 → 再検証」を自律ループする。検証フロー（構造確認 → 操作 → 結果確認 → ログ確認）は共通で、使うツールだけがバックエンドで変わる。

| バックエンド | 実体 | 強み | 主な用途 |
|---|---|---|---|
| `devtools` | Chrome DevTools MCP — **隔離・管理された** Chrome | 毎回クリーンな状態 / 安定した accessibility-tree の参照 ID / DevTools 品質の console・network 調査 | **localhost** のローカル検証・再現性重視・自律修正ループ |
| `cic` | Claude in Chrome — **ユーザーの実** Chrome セッション | 実ブラウザで目視 / 既存ログインセッションを流用 / GIF 記録 | **共有環境**（ログイン済セッションが必要な環境）・実機確認 |

## バックエンドの選択

1. **引数あり** → 指定されたものを直接起動（確認不要）
2. **引数なし** → 対象 URL から推奨を出して確認する
   - `localhost` / `127.0.0.1` → `devtools` 推奨
   - それ以外（共有の検証環境・本番） → `cic` 推奨（認証セッションが要るため）

既定は `devkit.json` の `verify.backend` / `verify.baseUrl`。

## 前提

```bash
DEVKIT_ENV=$(bash .claude/devkit/config.sh) || exit 1
eval "$DEVKIT_ENV"
```

- `devtools`: 対象アプリがローカルで起動していること
- `cic`: **操作前に接続ブラウザを必ず確認する**（`tabs_context_mcp`）。既存タブを勝手に使わず、新規タブを作る。前のセッションのタブ ID を再利用しない

ブラウザ操作ツールが遅延ロードされている場合は、**必要になりそうなものを 1 回の検索でまとめて読み込む**（1 つずつ読み込むと往復が無駄になる）。

## 合格基準（PASS 条件）

以下を全て満たせば PASS:

- **console error = 0 件**（warning は対象外）
- **主要な fetch / XHR が 2xx**。4xx / 5xx が 0 件
- **期待する UI 要素が実際に描画されている**（アクセシビリティツリー上に存在する）
- 操作を伴う検証では、**操作後の期待状態**（遷移先 URL / 表示テキスト / 保存結果）に到達している

4xx/5xx の判定は環境で揺れるので、**共有環境では「5xx は 0 件、4xx は許容上限つき」の 2 段**に緩めてよい（認証チェーンの 401 / prefetch の 404 が常態的に出る環境がある）。緩めた場合はレポートに明記する。

## 手順

### 1. 検証計画

何を確認するかを先に書き出す（対象 URL / 操作手順 / 期待結果 / 合格基準）。**書かずに操作を始めない** — 何をもって PASS とするかが後付けになる。

### 2. 自律ループ（最大 N 回。既定は `review.verifyRetries`）

各イテレーション:

1. **描画** — 対象 URL を開く。**必ず `https://` / `http://` から始まるフル URL を渡す**（スキームを省くと「遷移した」という応答が返るのに実際は遷移していないことがあり、後続の操作が意味不明なエラーで落ちて初めて気付く）
2. **構造確認** — アクセシビリティツリーを取得し、期待要素の有無を確認
3. **操作** — クリック / 入力 / 送信
4. **結果確認** — 遷移先・表示内容
5. **ログ確認** — console と network を取得し、合格基準に照らす
6. **判定** — PASS なら手順 3、FAIL なら原因を特定して修正し次イテレーションへ

#### フォーム入力の注意

**DOM の `value` を直接書き換えるツールは、React 等の制御されたコンポーネントの状態を更新しない。** `onChange` が呼ばれず、状態が空のまま送信されて API が空の値で呼ばれる。

- **クリックで focus → キー入力**（既存テキストを置き換えるならトリプルクリックで全選択してから）
- スクリプトで注入するなら、**ネイティブの setter を呼んでから `input` / `change` イベントを dispatch する**（`el.value = x` の直代入は拾われない）
- **日付入力は `YYYY-MM-DD` 形式で**。区切り文字を含む文字列をキー入力するとセグメント解釈で崩れる

#### 送信の注意

**ボタンのクリックが submit イベントまで発火しないことがある。** ネットワーク履歴にリクエストが 1 件も出ない場合は、フォームの submit をネイティブに発火させる方法（`form.requestSubmit()` 相当）に切り替える。切り分けは「対象のエンドポイントがネットワーク履歴に出現するか」で行う。

#### ダイアログの注意

**`alert` / `confirm` / `prompt` を発火させない。** ブラウザのモーダルは以降のイベントを全てブロックし、拡張が命令を受け取れなくなる。ダイアログを出しうる要素（削除ボタン等）は避けるか、事前にユーザーへ警告する。

### 3. PASS 報告 / 4. FAIL 報告（上限到達）

```markdown
## 検証結果
### バックエンド: devtools | cic
### 対象: <URL>
### 合格判定: PASS | FAIL（試行 I/N）
- console error: 0
- fetch 4xx/5xx: 0（許容上限を緩めた場合はその旨）
- 期待要素: <列挙>
### 挙動
### 検出エラー
### 次アクション
```

上限到達時は停止して報告する。

## 深追いしない

以下に該当したら**ループを続けず停止してユーザーに確認する**:

- ツール呼び出しが 2〜3 回連続で失敗する
- 拡張・MCP から応答が返らない
- 要素がクリックに反応しない / ページがロードされない
- 複数のアプローチを試しても完了できない

何を試して何が起きたかを述べ、どう進めるか尋ねる。**同じ操作を繰り返さない。**

## 進捗ログ

- 起動時: `▶ /verify-browser（backend=<...>, url=<...>）を起動`
- 各イテレーション: `🔁 Iteration I/N: <操作>`
- 判定: `✅ PASS（試行 I/N, console=0, 4xx5xx=0）` or `❌ FAIL（上限到達）`

## Notes

- 変更が UI に該当しないなら、その旨を述べてスキップする（無理に実行しない）
- **単体テストが緑でも、外部システムやフレームワークの実際の挙動に関する思い込みはここで初めて露見する。** モックを書くと思い込みがそのままモックに固定されるため、テストは緑のまま通る
- sub-agent 実行時にブラウザ MCP へ接続できない場合は、**接続できなかったことを明記して FAIL でなく「検証不能」として返す**（「問題なし」と報告しない）
