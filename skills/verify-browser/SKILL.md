# verify-browser — ブラウザ実機検証（合格判定 + 自律ループ）

画面を描画・操作・調査し、合格基準を満たすまで「検証 → 原因特定 → 修正 → 再検証」を自律ループする。検証フロー（構造確認 → 操作 → 結果確認 → ログ確認）は共通で、使うツールだけがバックエンドで変わる。

| バックエンド | 実体 | 強み | 主な用途 |
|---|---|---|---|
| `devtools` | Chrome DevTools MCP — **隔離・管理された** Chrome | 毎回クリーンな状態 / 安定した accessibility-tree の参照 ID / DevTools 品質の console・network 調査 | **localhost** のローカル検証・再現性重視・自律修正ループ |
| `cic` | Claude in Chrome — **ユーザーの実** Chrome セッション | 実ブラウザで目視 / 既存ログインセッションを流用 / GIF 記録 | **共有環境**（ログイン済セッションが必要な環境）・実機確認 |

## バックエンドの選択

1. **引数あり** → 指定されたものを直接起動（確認不要）
2. **引数なし** → 対象 URL から推奨を出して `AskUserQuestion` で確認する。**無断で選ばない**
   - `localhost` / `127.0.0.1` → `devtools` 推奨
   - 認証必須の共有環境 → `cic` 推奨（`devtools` はクリーンプロファイルなので**即ログイン画面に弾かれて検証できない**）
   - サインイン・ログインフロー**自体**を検証する → `devtools` 推奨（既存ログインが壊れたページを覆い隠さないように、セッション無しが要る）

既定は `devkit.json` の `verify.backend` / `verify.baseUrl`。

> **毎回の起動でバックエンドを確定し直す（前回を引き継がない）。** 同一セッションで再起動された場合も、その起動の引数だけで判定する。引数が無ければ**既に一度選んでいても**必ず確認する（ユーザーは切り替える目的で再起動していることが多い）。対象ルートも同様に引き継がない。

## 前提

```bash
DEVKIT_ENV=$(bash "$(git rev-parse --show-toplevel)/.claude/devkit/config.sh") || exit 1
eval "$DEVKIT_ENV"
```

- `devtools`: 対象アプリがローカルで起動していること。MCP 未接続ならその旨を報告して停止（`cic` での再実行を提案）
- `cic`: 拡張が接続済みで対象ドメインの権限が付与済みであること。新規タブを作り、既存のセッションタブは指示が無い限り再利用しない

ブラウザ操作ツールが遅延ロードされている場合は、**必要になりそうなものを 1 回の検索でまとめて読み込む**（1 つずつ読み込むと往復が無駄になる）。

### 接続ブラウザの確認（`cic` のみ・操作前に必須）

`cic` はユーザーの**実** Chrome を操作する。どの cookie・ログイン状態・付与済み権限が使われるかは**拡張が接続されている Chrome プロファイル**で決まる。意図しないプロファイルでの検証は誤判定（対象環境にログインしていない個人プロファイル等）を生み、テスト用認証情報の入力を個人・業務プロファイルで実行してしまうリスクがある。

**重要な区別**: 選べるのは**接続ブラウザ（拡張インスタンス）単位**であって、**Chrome のプロファイル自体は切り替えられない**。別プロファイルで検証したいなら、ユーザーがそのプロファイル側で拡張を接続し直す必要がある。

```
1. 接続ブラウザ一覧を取得
2. 操作前に AskUserQuestion で全接続ブラウザを 1 つずつ選択肢に列挙する
   （ラベル = 表示名、括弧内に識別子）。末尾に「各 Chrome 拡張に確認画面を出して
   そこで選ぶ」という選択肢を必ず加える。自分で勝手に選ばない
3. 選択されたブラウザに切り替えてから操作を始める
```

検証には普段使いより検証用に接続したプロファイルを優先する。個人・業務プロファイルしか無ければ、**その旨を明示してから**操作する。

## 合格基準（PASS 条件）

以下を全て満たせば PASS（バックエンド共通）:

1. **console error = 0 件**（warning は WARN 扱いで通過を阻害しない）
2. **主要な fetch / XHR が 2xx**。4xx / 5xx が 0 件（期待する 401 等は事前に許容リスト化する）
3. **期待する UI 要素が実際に描画されている**（アクセシビリティツリー上に存在する）
4. 操作を伴う検証では、**操作後の期待状態**（遷移先 URL / 表示テキスト / 保存結果）に到達している

判定を緩めてよい場面と、その作法:

- **4xx/5xx は自ドメインに絞って数える。** 解析タグ・広告・外部 SDK は環境都合で 4xx/5xx を返すことがあり、全リクエストを機械的に見ると毎回ヒットして不合格に見える。**除外したドメインと件数をレポートに明記する**（黙って落とさない）
- **共有環境では「5xx は 0 件、4xx は許容上限つき」の 2 段**に緩めてよい（認証チェーンの 401 / prefetch の 404 が常態的に出る環境がある）。緩めたらレポートに明記する
- **デプロイ直後の自ドメイン 5xx を即 FAIL にしない。** アプリではなく上流（リバースプロキシ / CDN）が返していることがある。切り分け順は (1) アプリのプロセス／Pod の起動からの経過時間と再起動回数、(2) アプリ側のログに同じステータスが出ているか、(3) **再ロードして取り直す**。再取得したこととその根拠を明記する

PASS しなかった項目の分類:

- **FAIL**: console error / 許容リスト外の 4xx・5xx / 期待要素の欠落 / 挙動の不一致 → 修正必須
- **WARN**: console warning / 許容リストに含まれる 4xx → 記録のみ、修正は任意

## ツールマッピング

以降の手順は**抽象ステップ**で書く。各ステップを選択したバックエンドのツールへ解決する:

| 抽象ステップ | `devtools` | `cic` |
|---|---|---|
| ページを開く | 新規ページを開く | 新規タブを作る → ナビゲート |
| 構造を読む | アクセシビリティツリーを取得（→ 参照 ID） | ページ読み取り / テキスト取得 |
| 要素を特定 | ツリー上の参照 ID | 要素検索 |
| クリック | 参照 ID を指定してクリック | 座標・要素指定のクリック |
| フォーム入力 | 参照 ID と値の組で入力 | フォーム入力ツール |
| ファイル添付 | ファイル入力要素へパスを渡す | ファイルアップロードツール |
| スクリーンショット | スクリーンショット取得 | スクリーンショット取得 / 記録は GIF 作成 |
| console ログ | console メッセージ一覧（error / warn） | console メッセージ読み取り |
| network | ネットワークリクエスト一覧（fetch / xhr） | ネットワークリクエスト読み取り |
| JS 実行 | スクリプト評価 | JavaScript 実行 |

**正確なパラメータ形は推測せず、ツール検索の結果に出るスキーマを読む。**

## エビデンス記録

保存先の準備・命名・秘匿情報の扱い・コメント形式は [エビデンス記録の共通規約](../../docs/evidence.md) に従う。本スキルの保存対象:

- **screenshot**: ステップ完了ごとに `screenshots/<NN>-<label>.png`（`NN` は連番）
- **console**: 試行ごとに `logs/console-R<試行番号>.txt`
- **network**: 試行ごとに `logs/network-R<試行番号>.jsonl`

### console / network 取得の落とし穴（`cic`）

🔴 **`cic` の console / network 読み取りは「そのツールを初めて呼んだ時点」から記録を開始する。** 検証を一通り終えてから呼ぶと「エラーなし」が返り、**「0 件だった」と「そもそも記録されていなかった」が区別できない**。対策は次のどちらか:

- 検証開始**前に**一度空打ちして記録を開始させる
- 検証後に**リロードしてから取り直す**（合格判定の証拠にするならこちらが確実。ページロードからの全リクエストが揃う）

**「取得に失敗した」と「0 件だった」を区別できない読み方をしない**のは、ログ・API・CI の判定すべてに共通する原則。

## 手順

### 1. 検証計画

何を確認するかを**先に書き出す**。書かずに操作を始めない — 何をもって PASS とするかが後付けになる。

- 変更ファイル（`git diff <base>...HEAD --name-only`）から影響ルートを推定する
- ユーザー指定のルートを優先する
- 期待 UI 要素・期待 fetch パス・許容 4xx を洗い出す

```
## 検証計画
- バックエンド: devtools
- 対象: <URL>
- 期待要素: <セレクタ / テキスト>
- 期待 fetch: <method> <path> → 2xx
- 許容 4xx: なし
```

### 2. 必須ルール

1. **操作前に必ず構造を読む。** 対象要素を確認してから操作する
2. **操作後に必ず結果を確認する。** 再読込 / スクリーンショットで変化を見る
3. **エラーが出たら次の操作へ進む前に原因を特定する**
4. **秘匿情報を出力に残さない**
5. **（`cic`）ネイティブダイアログを発生させない。** `alert` / `confirm` / `prompt` は以降のイベントを全てブロックし、拡張が命令を受け取れなくなる。出しうる要素（削除ボタン等）は避けるか、事前にユーザーへ警告する
6. 🔴 **書き込みを伴う検証は「その操作が何を巻き込むか」を先に読む。** 画面の警告文と実装を確認し、**巻き込み範囲をユーザーに提示して合意を取ってから**実行する。よくある罠は「一括更新」系で、**アップロードしたファイルに載っていないレコードを削除する**仕様のことがある（検証用に 1 行だけのファイルを上げると全件消える。正しくは全件をダウンロードして検証行を 1 行足す）

#### 書き込み検証の工学

- **ファイル添付は専用のアップロード操作で行う**（ファイル入力要素を指定する）。ボタンを普通にクリックすると **OS のファイルピッカーが開いて操作不能**になる
- **ツールが読めるディレクトリの制約に注意する。** ダウンロードフォルダ等を直接渡せないことがあるので、作業用ディレクトリへコピーしてからそのパスを渡す
- **大量データを書き換える操作は安全機構にブロックされうる。** 迂回せず、(a) 手順をユーザーに提示して手動実行を委ねる、(b) その観点は単体テスト側の担保に切り替える、のどちらかを**ユーザーに確認して選ぶ**。結果は「実機未実施」と明記して残す

#### 権限依存 UI の事前確認

ロールや権限で出し分けられる画面を検証するときは、**ログイン中のユーザーがそのロールを持つかを最初に確認する**。持っていないと対象の UI（管理者向けの切替 UI・メニュー項目）がそもそも描画されず、**シナリオが再現不能なのに「表示されない = バグ」と誤判定する**。開始時にスクリーンショットか構造読み取りでロール表示・該当メニューの有無を見て、無ければ適切なアカウントへの切替をユーザーへ依頼する。

### 3. 自律ループ（最大 N 回。既定は `review.verifyRetries`）

🔴 **自律修正ループが有効なのは `localhost` 対象のときだけ。** 共有環境（検証環境・本番）では影響回避のため**修正を適用せず報告のみ**にする。この判定は**バックエンドではなく対象 URL で決める**（`cic` でも localhost ならループしてよい）。

各試行 `R = 1..N`:

1. **描画** — 対象 URL を開く。**必ず `https://` / `http://` から始まるフル URL を渡す**（スキームを省くと「遷移した」という応答が返るのに実際は遷移しておらず、後続の操作が意味不明なエラーで落ちて初めて気付く）
2. **構造確認** — 期待要素の有無
3. **操作** — クリック / 入力 / 送信
4. **結果確認** — 遷移先・表示内容
5. **ログ確認** — console と network を取得し、合格基準に照らす
6. **判定** — PASS なら手順 4。FAIL なら 3.1 へ

#### 3.1 原因切り分け

- **console error**: スタックトレースから該当のコンポーネント / API 経路を特定する
- **5xx**: レスポンス本文とサーバログから原因（認証 / 権限 / データ層）を特定する
- **期待要素の欠落**: 条件分岐（フラグ / 権限）を grep で確認する
- **挙動不一致**: 期待と実態を表で並べる

#### 3.2 修正（`localhost` のみ）

原因が**ローカルコードの明確な不具合**なら修正して再検証する。修正後は開発サーバの再読込を待つ。**外部 API・共有環境の設定・認証情報**など修正不能な原因ならループを中断して報告する。

**ループ中の変更は `git status` で必ず把握する**（デバッグ用の書き換えや環境ファイルの改変が意図せず混入しやすい）。

#### フォーム入力の注意

**DOM の `value` を直接書き換えるツールは、React 等の制御されたコンポーネントの状態を更新しない。** `onChange` が呼ばれず、状態が空のまま送信されて API が空の値で呼ばれる。

- **クリックで focus → キー入力**（既存テキストを置き換えるならトリプルクリックで全選択してから）
- スクリプトで注入するなら、**ネイティブの setter を呼んでから `input` / `change` イベントを dispatch する**（`el.value = x` の直代入は拾われない）
- **日付入力は `YYYY-MM-DD` 形式で**。区切り文字を含む文字列をキー入力するとセグメント解釈で崩れる

#### 送信の注意

**ボタンのクリックが submit イベントまで発火しないことがある。** ネットワーク履歴にリクエストが 1 件も出ないなら、フォームの submit をネイティブに発火させる方法（`form.requestSubmit()` 相当）へ切り替える。切り分けは「対象のエンドポイントがネットワーク履歴に出現するか」で行う。

### 4. 報告

```markdown
## 検証結果
### バックエンド: devtools | cic
### 対象: <URL>
### 合格判定: PASS | FAIL（試行 R/N）
- console error: 0 / 想定 0 → ✅
- fetch 4xx/5xx: 0 / 許容 0 → ✅（除外: <外部ドメイン>）
- 期待要素: <列挙> → ✅
- 挙動: <期待> → ✅

### 挙動
| 操作 | 期待 | 実際 | 結果 |
|---|---|---|---|

### 検出エラー
| 種別 | 詳細 | 重大度 |
|---|---|---|

### 次アクション
```

上限に到達したら停止し、残存 FAIL・修正試行履歴・推定原因を出してユーザーに判断を仰ぐ（修正方針の合意 / 既知として見送り / 別 Issue 化）。

## よく使うパターン

抽象ステップで記載。ツールマッピングで解決する。

**ページ描画**: ページを開く → 構造を読む → スクリーンショット
**ログインフロー**: サインイン画面を開く → 構造を読む → 認証情報を入力 → 送信 → 遷移先を確認 → スクリーンショット
**エラー調査**: console（error/warn）→ network（fetch/xhr）→ 4xx/5xx を特定 → 現状をスクリーンショット
**フォームバリデーション**: 構造を読む → 不正値を入力して送信 → エラー表示を確認 → console を確認

## 深追いしない

以下に該当したら**ループを続けず停止してユーザーに確認する**:

- ツール呼び出しが 2〜3 回連続で失敗する
- 拡張・MCP から応答が返らない
- 要素がクリックに反応しない / ページがロードされない
- 複数のアプローチを試しても完了できない

何を試して何が起きたかを述べ、どう進めるか尋ねる。**同じ操作を繰り返さない。**

## 進捗ログ

- 起動時: `▶ /verify-browser（backend=<...>, url=<...>, max-retry=N）を起動`
- 各試行: `🔁 試行 R/N: <操作>`
- 修正: `🛠 <file:line> を修正 → 再検証`
- 判定: `✅ PASS（試行 R/N, console=0, 4xx5xx=0）` / `❌ FAIL（上限 N 到達 — 残: <内容>）`

## Notes

- 変更が UI に該当しないなら、その旨を述べてスキップする（無理に実行しない）
- 使用したバックエンドを出力に記録し、再実行の再現性を確保する
- **単体テストが緑でも、外部システムやフレームワークの実際の挙動に関する思い込みはここで初めて露見する。** モックを書くと思い込みがそのままモックに固定されるため、テストは緑のまま通る
- 🔴 **sub-agent として起動するとブラウザ MCP ツールがツールリストに降りず、ツール検索でも解決できないことがある。** その場合は (1) sub-agent 側は「バックエンド未接続 = **検証不能**」として即返す（無限リトライしない。**「問題なし」と報告しない**。エビデンスの無い FAIL コメントも投稿しない）、(2) 親セッションでブラウザツールを直接読み込んで同じ項目を実行する、(3) 証跡の保存とコメント投稿は親から行う
