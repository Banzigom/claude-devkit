# harvest — 知見の収穫

現在の会話を振り返り、有用な知見を抽出して `.claude/rules/` に永続化する。

`$ARGUMENTS`:

- `--pr`: 追記後に PR まで作る（既定は編集まで）

## Phase 1: 会話分析

**現在のコードや git history を読むだけでは得られない情報**に絞る。

### 抽出すべきもの

- **非自明な制約** — 自然にやると間違えるポリシー判断
- **ハマりポイント** — 実行順序の依存、壊れやすいパターン、間違えやすい操作
- **ユーザーからの指摘・修正** — アプローチの誤りを正されたケース。**これが最も価値が高い**
- **理由付きの設計判断** — コードに "why" が残らない判断

### 抽出すべきでないもの

- コードから読み取れる実装詳細（使用ライブラリ、ファイルパス、設定値、命名規則）
- 手順の転記（Makefile やワークフローに既にあるもの）
- ツール固有の使い方（ドキュメントであってルールではない）
- 既存の rules / CLAUDE.md と重複するもの

**判断基準**: 「コードと git history を読んだエンジニアがこれを見落とすか？」→ No なら抽出しない。

### 構造化

各知見を「タイトル / 追記先ファイル / 本文 / なぜ重要か（これが無いと何が起きるか）」で構造化する。

### 追記先の決め方

`.claude/rules/` の既存ファイルから、トピックが最も近いものを選ぶ。該当が無ければ新規作成する。**ファイル構成はプロジェクトごとに違う**ので固定の対応表を持たない — `ls .claude/rules/` で実物を見てから決める。

汎用の受け皿として `general.md`（言語・CI・命名等の横断）と `operations.md`（ブランチ運用・リリース・PR 規約）はテンプレで用意されている。

## Phase 2: 重複チェック

**最初に編集先の鮮度を確認する。** checkout は別作業のブランチに載っていることが常態で、そのまま Read / Edit すると**古い本文に対して重複チェックと追記をしてしまう**（既にマージ済みの他人の知見が見えず重複を作る / 是正したい既存行が古い版のまま）。

```bash
DEVKIT_ENV=$(bash "$(git rev-parse --show-toplevel)/.claude/devkit/config.sh") || exit 1
eval "$DEVKIT_ENV"
cd "$DEVKIT_ROOT"
git branch --show-current
git fetch origin "$DEVKIT_BASE_BRANCH" -q && git rev-list --count "HEAD..origin/${DEVKIT_BASE_BRANCH}"
```

**shallow clone だと比較系コマンドが無言で嘘の数を返す**（`git merge-base` が空を返し、`rev-list --left-right --count` はエラーなく無意味な数を返す）。先に確認する:

```bash
git rev-parse --is-shallow-repository   # true なら --unshallow してから比較する
```

ベースブランチ以外に居る、または behind なら**先にベース起点の worktree を作り、以降の Read / Edit をそこで行う**:

```bash
git worktree add -b harvest/<topic> ../<repo>-harvest "origin/${DEVKIT_BASE_BRANCH}"
```

このとき**現 checkout の作業中変更には一切触れない**（`git stash` も `git checkout --` もしない）。同一 checkout を複数セッションが共有していることがあり、`git checkout -b` した瞬間に他セッションの作業ブランチを奪う事故が起きる。

その上で、追記先の `.claude/rules/*.md` を Read し、既存の `## Learned` と同一概念がないか確認して、重複はスキップ候補にする。

## Phase 3: ユーザー承認

AskUserQuestion で知見を提示する（追記先ファイルも表示）。選択肢は **承認 / 編集して承認 / 却下 / 残り全て承認**。

## Phase 4: ルールファイルに追記

承認された知見を `## Learned` セクション末尾に追記する。セクションが無ければファイル末尾に作る。

- 1 知見 = 1 行の箇条書き（`- **` で開始）
- コード例は必要な場合のみインデント付きブロックで

**`- **` で始めること。** 肥大化チェック（Phase 6）はこの形をエントリとして数え、「知見が消えていないか」を base 比較で検証する。`- ` だけで書くとカウント対象外になり保全されない。

## Phase 5: CLAUDE.md・スキルの見直し

会話で得た知見が CLAUDE.md やスキルの内容に影響するなら更新提案を行う。

- **CLAUDE.md**: リポジトリ説明、ブランチ運用、リリースフロー、動作確認環境に古い情報がないか
- **スキル**: 手順の誤り、不足ステップ、改善できるフローがないか

## Phase 6: 肥大化チェック

`.claude/rules/` は**全ファイルが毎セッション自動読み込み**されるため、増え続けるとコンテキストを圧迫する。追記後に必ず検証する。

```bash
bash "$DEVKIT_ROOT/.claude/devkit/rules-size-check.sh"
```

**行数でなくバイト数で判定する。** Learned は「1 エントリ = 1 長行」形式のため行数は実態を捉えない（110 行で 48 KB になりうる）。

| 検証 | FAIL の意味 |
|---|---|
| 1 サイズ | 合計が上限超過 / ファイル単体が閾値超過 |
| 2 見出し保全 | base にあった見出しが消えた（移動は許容） |
| 3 エントリ保存則 | 知見の総数が減った（統合したなら `Merged-Entries: <n>` を書く） |
| 4 リンク解決 | 相対リンクの先が無い |
| 5 釣り合わせ | **増やしたのに退避していない** |

### 追記したら同じ変更で同量を退避する

🔴 **この harvest で `.claude/rules/` を 2 KB 超増やすなら、同じ PR で同等バイトを退避先へ移す。**

肥大化が繰り返される原因は、**harvest が追記だけを行い削減と非対称**なことにある。「気づいた人が後でアーカイブする」運用では再発が止まらないので、**増やした変更自身に釣り合わせを求める**（検証 5）。

- 退避先は `$DEVKIT_RULES_REF_DIR`（現役だが常駐不要）と `$DEVKIT_RULES_ARCHIVE_DIR`（解消済み・一度きり）。どちらも自動読み込みされない
- **消すのではなく動かす。** 検証 2（見出し保全）／検証 3（エントリ保存則）が消失を別途禁じている
- **本当に出せるものが無いときだけ `--allow-growth` を付ける。** 黙って増やせない形にするためのフラグなので、使ったら PR 本文に理由を書く

FAIL / 警告が出たら以下を提案する:

- **アーカイブ移動**（第一選択）— 一度きりの事故対応 / 仕組みで解消済み / 調査経緯の長文 / 低頻度 runbook を `$DEVKIT_RULES_ARCHIVE_DIR` へ全文移動し、rules 側にはクラス単位の 1 行ポインタを残す
- **常駐不要な仕様の移動** — 現役だが毎セッションは要らない仕様は `$DEVKIT_RULES_REF_DIR` へ
- 重複・類似エントリの統合（統合したらコミットメッセージに `Merged-Entries: <n>` を書く。書かないと保存則チェックが FAIL する）
- 実例・調査経緯の圧縮（結論と Issue/PR 参照は残す）

**何を移して何を残すかの判定基準は `.claude/rules/README.md`（P1〜P5 / A1〜A4）が SoT。** 踏み外し防止・同期必須ポイント・リスク高領域に紐づく知見はアーカイブ禁止。迷ったら常駐側に倒す。

## Phase 7: サマリー出力

```
## Harvest 結果
- 抽出 N 件 / 承認 M 件 / 却下 K 件
  - 保存先: .claude/rules/<file>.md (+X 件)
- CLAUDE.md / スキル更新: Y 件
- rules-size-check: PASS / FAIL（合計 <bytes> B）
```

## Phase 8（`--pr` 指定時のみ）: PR 化

Phase 2 で作った worktree でそのまま完結させる。

### コンフリクト解消

`.claude/rules/*.md` は全員が `## Learned` の**末尾に追記**するため、ベース起点で切った直後でも、作業中に別の harvest PR がマージされれば同じ行で必ず衝突する。**PR 作成時点で mergeable でも、マージ直前に衝突していることを前提に手順を組む。**

衝突には型が 3 つあり、解消方針が違う:

| 型 | 見え方 | 解消 |
|---|---|---|
| **末尾追記どうし** | 双方が `## Learned` 末尾に別の行を足した | **両エントリを残す**（別内容なので取捨選択は不要）。マーカー 3 行だけ削除 |
| **ベース側が整理で削除した** | 自分側は base から引き継いだだけの行を「自分の変更」として抱えている | **ベースの削除に追従**し、自分が編集した行だけ採用。両方残すとベースが消した行が復活する |
| **ベースが編集した節を自分が別ファイルへ移動した** | rules 側は削除で正しいが、移動先に旧内容が残る | マーカーを消すだけでは不足。ベースが**何を変えたか**を `git diff <merge-base> origin/<base>` で抽出し、**移動先ファイルへ手で反映**する |

2 型目の判定は `git show <merge-base>:<file>` と `git show origin/<base>:<file>` の該当行比較 — 一致していればベースは編集しておらず単に削除しただけ。

解消後は機械確認する:

```bash
grep -rn '^<<<<<<<\|^>>>>>>>' .claude/rules/ | wc -l   # → 0
git diff "origin/${DEVKIT_BASE_BRANCH}" --stat          # 自分の追記ファイルのみか
```

### push 前の確認

```bash
gh pr view <PR> --repo "$DEVKIT_REPO" --json state --jq .state   # → OPEN
```

**マージ済みの head へ push すると、削除されたブランチが「新規ブランチとして復活」し、修正コミットがどの PR にも乗らない宙吊りになる。** push 直後の mergeable は再計算ラグで古い値を返すのでポーリングして確認する。

### PR 本文

harvest PR は Issue を解決しないので、Issue 参照には `Refs` を使う（`Closes` は「この PR で解決した」の意味）。

## Notes

- **rules の追記は「増やす」だけでなく「移す・統合する」まで含めて 1 セット**。Phase 6 を飛ばすと必ず肥大化する
- 知見の粒度は「1 エントリ = 1 つの踏み外し」。複数の話を 1 行に詰めると後から統合も削除もできなくなる
