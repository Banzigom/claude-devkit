# pricing-change — 料金・単価の改定

**金額に直結するので、反映タイミングと過去分の扱いを必ず確定させてから実行する。**

## 起動時に確定させること

1. **対象**（全体 / 特定の契約・テナント / 特定のカテゴリ）
2. **新しい値**と**現在の値**
3. 🔴 **適用開始時点** — 月初から / 即時 / 指定日から
4. 🔴 **過去分をどう扱うか** — 遡って再計算する / 過去は凍結する

## Step 1: 現在の設定の確認

```bash
DEVKIT_ENV=$(bash .claude/devkit/config.sh) || exit 1
eval "$DEVKIT_ENV"
```

**設定の SoT がどこかを確定する。** 単価は「環境変数」「設定ファイル」「DB の上書きテーブル」の複数箇所に存在しうる。**優先順位を確認してから触る。**

## Step 2: 変更の適用

設定を編集する。**テンプレートから生成物を作る構成なら、生成まで実行して差分を確認する**（SoT だけコミットすると対象に反映されない）。

## Step 3: 反映タイミングの確認（最重要）

🔴 **保存 API を叩いた時点では請求額に反映されない構成がある。** 反映は集計処理の駆動による 2 段階になりがち:

| 段階 | 起きること |
|---|---|
| 保存直後 | 設定値は変わるが**金額は旧単価のまま**（表示と金額が食い違う中間状態） |
| 差分集計（短間隔） | **部分的に反映**される |
| 全体集計（日次等） | **完全に反映**される |

**「保存したので反映済み」と報告しない。** どの集計が走ったら反映されるかを確認し、**その時刻まで含めてユーザーに伝える。**

## Step 4: 過去分への影響確認

🔴 **月途中の変更は、当月分を月初まで遡って再計算されることがある**（月初切替を推奨する根拠）。

🔴 **過去月が変わらない担保は、機能によって強度が違う:**

| 担保の型 | 強度 |
|---|---|
| コードのガードで対象期間を制限している | **構造的に保証される** |
| 「集計処理が当月しか対象にしない」運用に依存 | **運用担保にすぎない**（別経路で過去月へ書き込むと壊れる） |

**この非対称を UI 文言で潰して共通化しない**（誤情報になる）。

**実測で確認する**: 変更前後で過去月の合計と単価が同じであること。

## Step 5: 表示系の確認

🔴 **「単価を設定値から再計算して表示する」経路があると、請求実績と乖離する。** 過去月の表示は**保存済みのスナップショット値**を優先して読む（設定の現在値を毎回読むと、改定のたびに過去月の表示金額だけが新単価で再計算され、発行済みの請求と食い違う）。

**スナップショット列が `0` の場合を「欠損」扱いして設定値へフォールバックしない**（過去月に現在単価が入って目的が壊れる）。フォールバックは**列の欠落 / null / 非数値のときだけ。**

## Step 6: コミット・PR・反映確認

- 変更内容・適用開始時点・過去分の扱いを PR 本文に明記する
- マージ後、**実際に反映されたことを金額で確認する**

## Step 7: 差分が出たときの切り分け

金額が合わないときは、🔴 **「差 ÷ 単価」で件数差に還元して、単価差か数量差かを先に切り分ける。**

1. カテゴリ別に**全件**突合して一致数を数える（**1 件だけ外れるのか全体がずれるのかで原因の層が変わる**）
2. 差額を単価で割って件数差に直す
3. **単価が一致していれば数量集計側、単価が違えば単価解決側**

## Notes

- 🔴 **設定に無い値・列は、追加以前の期間では欠損のまま残る**（過去分は再集計されない）。新しい列を読む表示は**必ず欠損時のフォールバックを持たせる**
- 🔴 **「利用実績ゼロでも最低料金が計上される」設計だと、作成直後の対象にも満額の請求が立つ。** 新規作成時は初月請求の要否を業務側に確認する
- 🔴 **自動決済がある場合、誤った請求行を放置すると毎日決済が試行されうる。** 「まだ課金されていないから急がない」は誤り
