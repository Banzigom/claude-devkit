# data-subject-operation — 個別データの削除・エクスポート

🔴 **不可逆かつ個人データを扱う。各ステップで確認を取り、勝手に進めない。**

## 基本方針

- 🔴 **削除は「対象の特定」と「実行」を必ず分ける。** 特定した内容をユーザーに提示して合意を取ってから実行する
- 🔴 **取得したデータを会話やファイルへそのまま貼らない。** 件数・集計値に落とす。**エクスポート成果物の受け渡し経路もユーザーと合意する**
- **削除中止条件を先に決める**（後述）

## 前提

```bash
DEVKIT_ENV=$(bash "$(git rev-parse --show-toplevel)/.claude/devkit/config.sh") || exit 1
eval "$DEVKIT_ENV"
```

対象環境への接続手段を確認する（[kube-debug-db](../kube-debug-db/SKILL.md)）。

## Step 1: 対象の特定

識別子（メールアドレス / ID）から対象レコードを一意に特定する。

🔴 **同じ識別子が複数の組織・テナントに存在しうる。** 対象を 1 件に絞れない場合は**実行せず**、候補を提示して確認を取る。

## Step 2: 影響の確認

**削除前に「その対象に紐づくもの」を数える:**

- 利用履歴・ログイン履歴（**一度でも利用しているなら削除の可否が変わる**）
- 他のレコードからの参照（外部キー・監査ログ・課金レコード）
- 論理削除で済むのか、物理削除が必要なのか

🔴 **論理削除で「触らないカラム」は復活時にそのまま蘇る。** 認証設定・権限・フラグが残ると、再登録したときに**意図しない状態で復活する**。削除の設計を確認する。

## Step 3: 最終確認（ゲート）

対象・件数・影響範囲・不可逆であることを提示して承認を取る。

**削除中止条件**（1 つでも該当したら実行しない）:

- 対象を 1 件に絞れない
- 利用履歴があり、業務側の合意が取れていない
- 課金・監査上の保持義務がありうる
- **本番環境で、バックアップの存在が確認できていない**

## Step 4: 実行

🔴 **複数テーブルに跨るならトランザクションで実行する。** 途中で失敗して**参照先だけ消えた中途半端な状態**を作らない。

**実行前に対象件数を数え、実行後の削除件数と一致することを確認する。**

## Step 5: 検証

- 対象が消えている / エクスポートできていること
- **関連レコードが期待どおりの状態であること**（残すべきものが残り、消すべきものが消えている）
- **他の対象に影響が出ていないこと**（件数の before / after）

## Step 6: 報告

```
<delete|export> 完了
- 対象: <識別子>（<組織 / テナント>）
- 影響: <テーブル別の件数>
- 検証: before <N> → after <M>
- 成果物の受け渡し: <合意した経路>   ← export の場合
```

## Notes

- 🔴 **一括操作の巻き込み範囲を先に読む。** 「一括更新」系の機能には、**ファイルに載っていないレコードを削除する**仕様のものがある。**検証用に 1 行だけのファイルを上げると全件が消える**
- **大量データを書き換える操作は安全機構にブロックされうる。** 迂回せず、手順をユーザーに提示して手動実行を委ねる
- エクスポート成果物に個人データが含まれる場合、**保存先と保持期間をユーザーと合意する**
