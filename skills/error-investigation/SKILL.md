# error-investigation — 障害の切り分け

🔴 **調査のみ行い、修正はしない。** 修正が必要なら報告してユーザーの判断を仰ぐ。

## 手順

### 1. 状況の確認

```bash
DEVKIT_ENV=$(bash .claude/devkit/config.sh) || exit 1
eval "$DEVKIT_ENV"
```

聞くこと: **対象**（環境 / テナント）/ **症状**（何が起きているか）/ **発生時期**（いつから）/ **影響範囲**（全員か特定条件か）。

🔴 **「画面名」「操作」を具体的に確定させる。** 症状の言い換えのまま調査に入ると、まったく別の経路を追うことになる。ユーザーが使った文言（メニュー名・ボタン名）がそのまま grep のキーワードになることが多い。

### 2. 「顕在化した変更 ≠ 原因の変更」を先に切り分ける

🔴 **直近マージされた PR を反射的に犯人扱いしない。**

1. 失敗ログからエラーの識別子（マイグレーション名 / ファイルパス / 関数名 / SQL / 列名）を抜く
2. `git log --all --oneline --diff-filter=A -- '*<識別子>*'` で**その識別子を追加したコミット**を特定する
3. `gh api repos/OWNER/REPO/commits/$SHA/pulls` で原因 PR と時刻を確定する
4. 直近の PR の差分にその識別子が**無い**ことを確認する（`gh pr diff <N> | grep -c '<識別子>'` が 0）

### 3. 稼働状態の確認

```bash
kubectl get pods -n <ns>
kubectl describe pod -n <ns> -l app=<svc>
```

| 状態 | 意味 |
|---|---|
| `CrashLoopBackOff` | 起動に失敗している |
| `OOMKilled` | メモリ不足で強制終了 |
| `ImagePullBackOff` | イメージ取得に失敗 |
| 再起動回数が異常に多い | 起動直後に落ちている |

**image tag が期待する版か**も確認する（未デプロイを障害と読み違えない）。

### 4. ログの確認

症状から見るべきサービスを決める（入口 → 中継 → バックエンド の連鎖で追う）。

```bash
kubectl logs -n <ns> deployment/<svc> --tail=500 | grep -iE "error|exception|fatal"
```

🔴 **ログが静かなことを「そこに到達していない」と読まない。** エラーハンドリングがログ出力を条件付きにしていると、利用者にエラーを返しながら**ログに 1 行も残らない**。その場合はエラー収集 SaaS・上流プロキシのアクセスログが唯一の手掛かりになる。

🔴 **同じステータスコードでも意味が複数あることがある。** メッセージまで見て「該当なし（正常）」と「本当の失敗」を区別する。**一律に 5xx として扱うと、正常な『該当なし』が障害報告になる。**

### 5. データ層の確認（必要に応じて）

- マイグレーションの適用状態
- アクティブ接続数と上限
- DB インスタンスの状態（`/db-status`）

**「スキーマにあるが DB に無い列」を要求していないか**を疑う。ORM が明示列指定なしで全列を取りに行く構成では、**その機能に一切触れていないコードまで巻き込んで落ちる。**

### 6. 結果報告

1. **原因の特定 / 推定** — 根拠（ログ行・コミット・PR）を添える
2. **影響範囲** — この環境だけか、他にも波及しうるか
3. **推奨アクション** — 再起動で復旧 / アプリ修正が必要 / データ修正が必要 / 切り戻し（`/app-rollback`）/ インフラ対応

🔴 **修正は行わず、ユーザーの判断を仰ぐ。**

## Notes

- **恒常的に失敗しているジョブを「いつもの失敗」で片付けない。** 本物の失敗がそのノイズに埋もれる。定期実行なら「一度でも成功したことがあるか」を確認する（一度も無いなら設定ミスを疑う）
- **エラー報告の Issue を立てるなら、タイトルは `[bug] <症状要約>（<原因の一言>）` にし、原因側の担当者へ cc する**
