# security-review — リリース前セキュリティ監査（全リポ横断）

**差分だけのレビューではない。** 各リポジトリのコードベース全体をスキャンし、さらに**システム全体を統合的に**見る。

これはローカル実行のスキル（CI 連携なし）。検出・報告までを担い、**修正は行わない**。

## 対象リポジトリ

```bash
DEVKIT_ENV=$(bash "$(git rev-parse --show-toplevel)/.claude/devkit/config.sh") || exit 1
eval "$DEVKIT_ENV"

{ printf '%s\t%s\n' "$(basename "$DEVKIT_ROOT")" "$DEVKIT_ROOT"
  jq -r '.siblingRepos[]? | [.name, .path] | @tsv' "$DEVKIT_CONFIG"
}
```

起動時に対象をユーザーへ確認する（全リポ / 一部）。**clone されていないリポは「未スキャン」として明記**する（黙って飛ばすと「問題なし」と誤読される）。

## レビュー観点（リポ単体）

1. **インジェクション** — SQL / コマンド / XSS / テンプレート
2. **認証・認可** — 認証の欠落、権限昇格、安全でないセッション管理
3. **機密情報の露出** — ハードコードされた秘密情報・API キー、ログへの個人情報出力
4. **入力検証** — API エンドポイント・フォーム入力での検証不足。**Content-Type を検証せず下流へ pass-through していないか**
5. **アクセス制御** — 直接オブジェクト参照、認可漏れ、不適切な CORS
6. **暗号** — 弱いアルゴリズム、安全でない乱数、鍵管理
7. **設定** — 安全でない既定値、本番でのデバッグモード、CSP / セキュリティヘッダ
8. **エラー処理** — エラーメッセージ・スタックトレース経由の情報漏洩
9. **依存ライブラリ** — サードパーティの危険な使い方
10. **インフラ** — コンテナ定義の不備、環境変数の扱い、ポート露出

## レビュー観点（システム横断 — 必須）

リポ単体スキャンに加え、**入口から出口までのデータフロー**を追う。**これが無いと意味が無い。**

- **認証情報の連鎖** — 入口で発行した資格情報が下流へどう渡り、どこで検証されるか。発行・検証・期限・改竄耐性が end-to-end で一貫しているか。**「中継層が受け取ったヘッダをそのまま流している」箇所は必ず追う**
- **テナント / 組織の分離** — 分離を担保している仕組み（行レベルセキュリティ・クエリ条件・ミドルウェア）が**全経路**で効いているか。**片方の層だけ直して他方を忘れると、UI からは見えなくても API 直叩きで越境できる**
- **権限フィルタの一貫性** — ある画面で絞っている条件が、別経路（管理系 API・バッチ・エクスポート）でも同じく効いているか。**管理者バイパスが意図的なものか、漏れか**を区別する
- **アップロード / 外部ストレージ** — 署名付き URL の発行条件・有効期限・Content-Type 検証が各層で揃っているか。**サーバがファイルの中身を一度も見ない経路**では、アップロード時の検証は成立しない（実効的なゲートは保存・利用時）
- **利用量・課金** — カウントの改竄・スキップ経路がないか

## 既知の許容項目

`.claude/security-review/known-acceptable.md` があれば読み込み、**そこに記載のものは報告しない**。無ければ作成を提案する。

## False Positive を避けるフィルタ

🔴 **実在する具体的な攻撃経路に高い確信がある指摘のみ報告する。** 以下は報告しない:

- **具体的な exploit が無い理論上の問題**（ランタイムが既に弾いているもの）
- **実際の脆弱性が無い多層防御の提案**（既存コード経路が既に権限昇格を防いでいる場合）
- **デプロイ構成で緩和済みの問題**（既定値が危険でも、本番ビルドで明示的に上書きされている等）
- **開発フローを壊す変更**（明確なセキュリティ利得が無い限り）
- **信頼できる入力**（環境変数・CLI フラグ・シークレット管理下の値）。これらの制御を要する攻撃は報告しない

各指摘で自問する: **「本番のデプロイ構成を前提に、未認証の攻撃者（または低権限ユーザー）が現実的にこれを exploit できるか？」** 答えが「理論上だけ」「管理者権限が必要」なら報告しない。

## 手順

1. 対象リポを確認する（`AskUserQuestion`）
2. `known-acceptable.md` を読み込む
3. 各リポをスキャンする（リポ単体 10 観点）。`grep` / `find` / Read で**証拠となる行**を集める
4. システム横断観点でデータフローを追う
5. 結果を出力する

## 出力フォーマット

```markdown
## セキュリティレビュー結果

**サマリー**: Pass / Fail（CRITICAL または HIGH の指摘あり）
**スキャン対象**: <リポ列挙>　**未スキャン**: <未 clone のリポ>

### リポ別の指摘
- **Severity**: CRITICAL / HIGH / MEDIUM / LOW
- **Repo / File**: <repo> <path:line>
- **Issue**: 説明（攻撃経路を具体的に）
- **Remediation**: 修正案

### システム横断の指摘
- 同形式。関与するリポ・ファイルを複数列挙する
```

指摘が無ければサマリー行（Pass）のみ。**known-acceptable 項目の説明・良い点の称賛・付帯コメントは含めない。** actionable な指摘とサマリーだけに絞る。

## Notes

- 差分ではなく**コードベース全体 + システム横断**を見る
- 新たに許容と判断した項目は `known-acceptable.md` への追記をユーザーに提案する
- **修正の実施は別途**（このスキルは検出・報告まで）
- 🔴 **秘密情報をファイルから消しても、バージョン管理の履歴には残る。** 「ファイルから削除した」を「漏洩を止めた」と書かない。**実際に塞ぐには当該資格情報のローテーションが要る**ことを Remediation に明記する
