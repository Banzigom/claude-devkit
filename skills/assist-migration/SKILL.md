# assist-migration — スキーマ変更とマイグレーション

```bash
DEVKIT_ENV=$(bash "$(git rev-parse --show-toplevel)/.claude/devkit/config.sh") || exit 1
eval "$DEVKIT_ENV"
jq -r '.database.schemas[]? | [.name, .path, .engine, .migrateCommand] | @tsv' "$DEVKIT_CONFIG"
```

`database.schemas` が空なら、**スキーマファイルの場所とマイグレーションコマンドをユーザーに確認**し、設定への追加を提案する。

## 前提

🔴 **マイグレーションの生成にはローカル DB の起動が必須**（適用済みマイグレーションとの照合が要るため）。落ちていると接続エラーになる。

🔴 **手書き SQL で回避しない。** 回避すると (a) 他のマイグレーションと timestamp が衝突する、(b) 差分検出と乖離して次回の生成で再作成・再適用される、の二重リスクを負う。**DB を起動してから作る。**

## フロー

本番稼働中のシステムでは、常に**増分マイグレーション**を積む（リセットしない）:

1. 空のマイグレーションを生成する（`emptyMigrateCommand`）
2. 生成された SQL を編集する
3. 適用する（`migrateCommand`）

## スキーマ変更の影響チェックリスト

- [ ] **既存データへの影響**（NULL / 既定値 / 型変換）
- [ ] **NOT NULL は段階追加**（下記）
- [ ] **外部キーの削除時挙動**（Cascade / SetNull / Restrict）
- [ ] **カラム・テーブル改名時は物理名を保持するマッピングを付ける**（改名 = drop + add にしない）
- [ ] enum 値の追加・削除の影響
- [ ] **DROP を含むなら、他リポのスキーマ同期とデプロイ順序**（下記）

## 命名規約

**論理名（コード側）と物理名（DB 側）の変換規則を既存に揃える。** 差分はマッピング指定で吸収する。新規だけ別規則にすると、ツールの自動生成と食い違う。

## 行レベルセキュリティ（テナント分離がある場合）

テナント単位で永続化するテーブルの標準形:

- `tenant_id` を NOT NULL で持つ
- 親テーブルへの外部キー（削除時 CASCADE）
- **RLS 有効化 + 分離ポリシー + バイパス用ポリシーの 2 本**
- 値域は DB の CHECK 制約で守る

```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation_policy ON <table>
  USING (tenant_id = current_setting('app.current_tenant_id'));
```

🔴 **エンジンによっては CHECK 制約をスキーマ定義で表現できない**（生成された SQL を直接編集して足す）。金額・単価・数量など**非負であるべき数値カラムに CHECK が無いのは指摘対象**。最初から入れる。

🔴 **ユニーク制約に NULL 許容カラムを含めると、エンジンによっては NULL 同士を重複と見なさない**ため一意性が崩れる。optional な識別子をキーに含めるなら、**空文字や sentinel 値で NOT NULL に倒す**。

## インデックス設計

| 対象 | 理由 |
|---|---|
| 外部キーのカラム | JOIN 性能 |
| WHERE で絞るカラム | 検索性能 |
| ORDER BY のカラム | ソート性能 |

「絞り込み + 並び替え」を意識した複合インデックスを設計する。**全外部キーにインデックスがあるか / 重複・未使用が無いか**を確認する。

## よくあるパターン

### NOT NULL カラムの追加（段階適用）

🔴 **既存データのあるテーブルにいきなり NOT NULL を入れない。** 3 つに分ける: (1) nullable で追加 → (2) 既存行を backfill → (3) NOT NULL 制約を追加。

### 論理削除がある場合

**削除時に触らないカラムは、復活時にそのまま蘇る。** 「削除時に消す」ではなく**「復活時にリセットする」**で塞ぐ。復活を伴う機能を作るときは、対象テーブルの列を一度洗う。

## デプロイ順序（他リポとスキーマを共有している場合）

🔴 **列の追加と削除で順序が真逆になる。** マイグレーションを実際に流すのはどのリポか（＝列の生死を切り替えるのはどれか）で決まる:

| 変更 | 正しい順序 | 先に出してはいけない側 |
|---|---|---|
| 列を **追加** | **マイグレーションを流す側 → 他リポ** | 他リポ（DB にまだ無い列を要求する） |
| 列を **削除** | **他リポ → マイグレーションを流す側** | マイグレーションを流す側（消えた列を他リポが要求し続ける） |

**「片方を先に出せば安全」と一般化しない。** ORM が明示列指定なしで全列を取りに行く構成では、**その機能に一切触れていないコードまで巻き込んで落ちる。**

## 手順

1. 対象スキーマと現行定義を Read する
2. 変更を分析し影響を特定する（既存データ / 外部キー / インデックス / 命名 / RLS）
3. インデックス・段階適用の要否を判断して提案する
4. スキーマを編集する
5. 空マイグレーション生成 → SQL 編集 → 適用。**RLS が要るテーブルはポリシーを SQL に追記する**
6. 結果と次アクション（`/schema-sync` の要否）を出力する

## Notes

- **破壊的変更・ダウンタイムを伴うものは計画を提示してユーザー確認を取る**
- 🔴 **共通 DB に対する「条件付き INSERT」の data migration は、条件を満たすデータがまだ無い環境で警告なくスキップされる。** マイグレーションは一度記録されると再実行されないので**二度と入らない**。**投入確認 SQL を SQL 内にコメントで残し、手動投入の経路を用意する**
