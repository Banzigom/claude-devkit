# multi-surface-change — 多段配線の追加 / 廃止

**プロジェクト固有の手順書の「骨格」。** 実際に触るファイルはプロジェクトごとに違うので、**このスキルは進め方と検証の型だけを持つ。** 具体の配線先は `.claude/rules/` の同期必須ポイント表（無ければ手順 1 で作る）が SoT。

**このパターンが当てはまる作業の例**: AI モデル・決済プラン・テナント・機能フラグ・通知チャネル・課金カテゴリの追加 / 廃止。

🔴 **専用の手順書があっても、要件定義（`/define-requirements`）→ 設計（`/design-implementation`）のゲートを先に通す。** 専用スキルは「実装」フェーズの道具であって、フロー全体の代替ではない。**いきなりブランチを切って実装に入らない。**

## 手順

### 1. 配線先の棚卸し（最重要）

`.claude/rules/` の同期必須ポイント表を引く。**該当する行が無ければ、この作業で表に行を足すところから始める。**

表に無い / 表が古い場合の洗い出し方:

```bash
# 概念の識別子（既存の同種エントリ）を全リポで引く
grep -rn "<既存の同種の識別子>" --include='*.ts' --include='*.js' --include='*.py' --include='*.tf' . ../<sibling>/
```

🔴 **「定義元」だけでなく「派生表」まで洗う。** 元の一覧から機械生成される別の表・列・CSV があると、**元だけ直しても派生に露出し続ける**。`grep -rn "<定義元の識別子>"` で参照元を全数列挙する。

🔴 **UI で隠すだけでは塞げない。** 選択肢を消しても API を直接叩けば通る経路が残る。**表示のフィルタとサーバ側のゲートは別々に確認する。**

洗い出し結果を表にする:

| # | レイヤ / リポ | ファイル | 変更内容 | 検知手段（型 / テスト / 目視） |
|---|---|---|---|---|

**「型エラーで気付ける」「実行時に落ちる」「何も起きない（サイレント）」に分類する。** サイレントな箇所が最も危険なので、**ソース固定テストで機械検証を足す。**

### 2. 追加 / 廃止の別で進め方を変える

#### 追加

1. **定義元 → 参照元 → 設定 / インフラ** の順に足す
2. **既定は「無効」に倒す。** 非同期に解決されるフラグを表示条件に使うなら、**初期値は隠す側**にする（解決前の一瞬の誤露出を防ぐ）
3. **外部サービス側の前提**（プロバイダでの有効化・デプロイ・払い出し）は**コードと別に必要**。**先に済ませないと疎通確認ができない**

#### 廃止（2 段階に分ける）

| 段階 | 内容 | 理由 |
|---|---|---|
| **Phase 1: 見えなくする** | 選択肢・UI・許可リストから外す | **利用者への影響を先に止める。** ロールバックも容易 |
| **Phase 2: 完全削除** | 集計ロジック・バックエンド・設定・DB 列を消す | 過去データの集計に影響するので**Phase 1 の安定を確認してから** |

🔴 **Phase 1 の前に検証データを作る。** 消してから「過去分が正しく残っているか」を確認しようとしても、**確認する手段ごと消えている。**

🔴 **「無効フラグを立てる」が集計に効くとは限らない。** 表示から外すフラグと、集計の対象条件は別物のことが多い。**両方を確認する。**

### 3. 段階リリースと順序

- **設定・インフラ側の配布が先か、アプリ側が先か**を決める。必須の設定が未配布のままアプリを出すと**起動時の検証で落ちる**
- スキーマ変更を伴うなら [assist-migration](../assist-migration/SKILL.md) のデプロイ順序表に従う（**追加と削除で順序が真逆**）
- **片側だけがデプロイされている窓が必ず存在する。** 新旧どちらのリクエストも受けられるガードを入れ、**全環境へ行き渡ってから旧経路を消す**

### 4. AS-IS / TO-BE チェックリストで検証

実装後、**変更前の状態と変更後の期待状態を 1 行ずつ並べて確認する:**

```markdown
| # | 確認項目 | AS-IS（変更前） | TO-BE（期待） | 実測 | 判定 |
|---|---|---|---|---|---|
| 1 | 選択肢に出るか | 出る | 出ない | 出ない | ✅ |
| 2 | API 直叩きで通るか | 通る | 拒否される | 拒否 | ✅ |
| 3 | 過去分の集計 | N 件 | N 件（不変） | N 件 | ✅ |
```

🔴 **「変わったこと」だけでなく「変わっていないはずのこと」も確認する。** 廃止作業で過去データの集計が変わるのは事故。

### 5. 回帰防止を仕組みに残す

- **同期必須ポイント表に行を足す**（次に同じ作業をする人が洗い出しからやり直さないため）
- **サイレントに壊れる箇所にソース固定テストを足す** — ただし**「呼び出しの存在」しか見ないテストは、無効化を検知できない**（`if (false && ...)` でも文字列は残る）。守りたい判定は**純関数へ切り出して振る舞いで固定する**
- **書いたテストは変異検証で確かめる**（1 箇所だけ壊して FAIL することを実測する）

## Notes

- 🔴 **答えが出せる仕様項目は要件定義で確定させる。** リージョン・上限値・API バージョン・単価・対象範囲は、聞けば決まる。「未解決事項」に残したまま設計へ先送りしない
- 🔴 **重複エントリは「後勝ち」や「二重加算」として無音で通ることがある。** 一意性を機械検証するテストを置く（金額の二重計上は直接的な損害になる）
- 廃止したものを**戻す**ときは、撤去コミットのメッセージで**「なぜ撤去されたか」**を読む。コード削除ではなく**方針判断**だったなら、戻すことは当時の判断を覆すことになる
