# .claude/rules/ の運用基準

`.claude/rules/` は**全ファイルが毎セッション自動読み込み**される。そこに置いてよいのは「**次のセッションで踏み外しを防ぐもの**」だけ。

一度きりの事故対応や、仕組みで解消済みの手順は、**失うのではなく移す**。移動先は 2 つ:

| 置き場 | 性質 | 読み込み |
|---|---|---|
| `.claude/rules/` | 踏み外し防止・同期必須ポイント・現に判断へ使う運用ルール | 毎セッション自動 |
| `docs/rules-reference/` | 現役だが常駐不要なドメイン仕様（設定値一覧・プラン仕様・UI 基準等） | 必要な時に開く |
| `docs/rules-archive/` | 過去の個別事故・解消済み手順・調査経緯 | 必要な時に grep |

アーカイブは `.claude/rules/` と **1:1 対応**させる（`operations.md` → `docs/rules-archive/operations.md`）。

## 探し方

**「rules に無いから知見が存在しない」と判断する前に、必ず検索する。**

```bash
grep -rn "<キーワード>" docs/rules-reference/ docs/rules-archive/
```

## 判定基準

残すか移すか。**常駐必須クラスに 1 つでも該当すればアーカイブしない**（常駐判定が優先）。

### 常駐必須クラス（アーカイブ禁止）

| ID | クラス | 理由 |
|---|---|---|
| **P1** | 同期必須ポイント表（1 つ直したら必ず一緒に直す箇所の対応表）から参照される知見 | 参照が切れると横展開漏れ = デグレ検知率が落ちる |
| **P2** | 他の rules・スキルから「〜が SoT」として参照されている記述 | リンク切れ・SoT 喪失 |
| **P3** | **踏み外し防止**（自然にやると間違える、高頻度操作の罠） | 次のセッションで即使う。消すと同じ失敗を繰り返す |
| **P4** | リスク高領域（課金 / 認証 / 権限 / データ分離 等、壊れると事業影響が大きい領域）に紐づく設計判断 | 誤ると障害・金銭影響に直結 |
| **P5** | 現に判断へ使うアクティブな運用ルール（「このツールは廃止済みなので対応不要」等） | 消すと誤った運用に戻る |

### アーカイブ対象クラス

| ID | クラス | 例 |
|---|---|---|
| **A1** | 一度きりの事故対応記録（再発可能性が低い個別復旧手順） | 特定リソースの手動削除手順、state 破損からの復旧 |
| **A2** | 仕組みで解消済み・自動化済み（人が知る必要がなくなったもの） | 自動化された掃除手順、修正済みの CI flaky |
| **A3** | 調査経緯・実測ログ（結論だけ残せば足りる長文） | 「N 件中 M 件が失敗し 2 段 retry で完走」等の実測値の羅列 |
| **A4** | 低頻度の runbook 相当手順（発生時に検索すれば足りる） | 年に数回の運用手順の細部 |

**迷ったら常駐側に倒す。** 削りすぎのほうが害が大きい。

### この分類軸を採る理由

| 候補 | なぜ不採用か |
|---|---|
| 経過月数ベース（古いものをアーカイブ） | **古い知見ほど価値が高いことが多い**（環境固有の落とし穴は古いが常駐必須）。逆効果 |
| 参照頻度ベース | rules は自動読み込みで一括のため、**エントリ単位の参照頻度を観測できない** |
| **性質ベース（P1〜P5 / A1〜A4）** | 「次のセッションで使うか」という本来の判断軸に一致。禁止クラスを明示できるため誤アーカイブを構造的に防げる |

## 書き方の規約

### 知見エントリ

`## Learned` 配下に **1 知見 = 1 行**、`- **` 始まりで書く。

```markdown
## Learned

- **<結論を先に書く>** — <理由 / 何が起きるか>。<必要なら実例や参照>
```

**`- **` で始めること。** `rules-size-check.sh` の保存則チェックがこの形を数え、「知見が消えていないか」を base 比較で検証している。`- ` だけだとカウント対象外で保全されない。

### アーカイブ側

元ファイルの見出し構造を保ち、エントリを**全文のまま**移す（要約しない — 要約は rules 側のポインタが担う）。

### rules 側のポインタ

各 rules ファイルの `## Learned` 末尾に、**クラス単位**で置く（エントリ単位にすると数百件のポインタで数十 KB を消費し、削減の意味が消える）。

```markdown
### アーカイブ済み

以下は [docs/rules-archive/operations.md](../../docs/rules-archive/operations.md) に全文保管（自動読み込み対象外）。

- 個別リソースの手動復旧手順（A1）
- 自動化済みの掃除手順（A2）
```

ポインタ行は **`- ` 始まりで `**` を使わない**。保存則チェックが `^- \*\*` を数えるため、`**` を付けるとポインタが知見エントリとして二重計上される。

### エントリを統合したとき

同型のエントリをまとめて件数が減る場合は、コミットメッセージにトレーラーを書く。書かないと保存則チェックが「知見が消えた」と判定して FAIL する。

```
Merged-Entries: 3
```

## 検証

移動・統合・圧縮のたびに手元で実行する。

```bash
bash .claude/devkit/rules-size-check.sh
```

| 検証 | 内容 |
|---|---|
| 1. サイズ | 合計が上限以下か（`.claude/devkit.json` の `rules.maxTotalBytes`） |
| 2. 見出し保全 | base との**分岐点**比較で見出し（`^#`）の削除・改名がゼロか。**ファイル間の移動は許容** |
| 3. 知見エントリ保存則 | `^- **` の総数が base から減っていないか |
| 4. リンク解決 | 相対リンクの実ファイルが存在するか |
| 5. 釣り合わせ | rules を増やした分だけ退避先へ**移した**か（ラチェット）。出せるものが無いときだけ `--allow-growth` で宣言する |

比較対象は base ブランチの**現在の tip ではなく分岐点**。tip と比べると、rules に一切触れていない PR でも、レビュー待ちの間に並走 PR がマージされるだけで FAIL する。

### 上限の決め方

**上限は「ローカルの実測値ちょうど」で決めない。** base の最新 + 余裕（20 KB 程度）にする。実測値ちょうどにすると、知見を 1 件足しただけで base 自身が FAIL する状態になり、無関係な PR が巻き添えで落ちて「気づいた人が都度アーカイブして帳尻を合わせる」運用に転落する。

削減が進んだら上限を下げ直す（ラチェット方式）。**上限に当たったときの第一選択は「判定基準に従って移す」であって「上限を上げる」ではない。**

## 検証自身の検証

**機械検証を新設・修正したら、その検証自身を故意破壊で確かめる。** 検証スクリプトは「PASS しているから正しい」と信じられやすく、緩すぎ・厳しすぎの両方向に壊れる。

作法: 本物のエントリを 1 件だけ消して **FAIL を確認 → 復元して PASS を確認**。偽陽性を消したときは特に必須（「エラーが出なくなった」と「検知しなくなった」の区別がつかないため）。

🔴 **見るのは「❌ が出たか」ではなく exit code。** 検知はできているのに終了ステータスに伝わらない壊れ方が最も見つかりにくい。実際に踏んだ 2 パターン:

- **ローカル変数だけ立てて集約変数に伝えていない**（`sub_ng=1` は立つが `FAILED` は 0 のまま）
- **`... | while read` でループがサブシェルに入り、加算が呼び出し元に残らない**（`while ... done < <(...)` にする）

どちらも `❌` を表示しながら exit 0 で通る。**故意破壊のたびに `echo $?` まで見ること。**
