# テスト方針

何にテストを書き、何を除外し、どこを CI の必須ゲートにするか。

運用基準は [README.md](./README.md) が SoT。

## 必須 / 除外

| 区分 | 例 |
|---|---|
| **必須** | ビジネスロジック・分岐・境界値 / バグ修正の回帰テスト / 権限・認可の判定 / 金額・数量の計算 / 外部 API 呼び出しの引数とヘッダ |
| **除外** | 見た目（styling / visual）のみのコンポーネント / 自動生成コード / 設定値の単純な読み出し |

**grey zone は「振る舞いを持つか」で切る。** 見た目のコンポーネントでも、件数しきい値・開閉・並び替え等の*振る舞い*を持つならテスト対象。除外の「見た目」は styling/visual を指す。

## テストの品質基準

- **「テストが通ること」と「テストがバグを捕まえること」は別**。回帰テストを書いたら、**修正を一時的に戻して落ちることを実測**し、その結果を PR に書き残す（コードに残らない検証なので、書かないと後から追えない）
- **変異検証は対象をコミットしてから行う**。未コミットの編集に `git checkout -- <file>` を打つと自分の変更ごと消える。手順は (1) 実装とテストをコミット → (2) 変異を適用 → (3) FAIL とテスト名を記録 → (4) `git checkout -- <file>` → (5) `git status --short` が空（新規テストは untracked なので `??` で残るのが正常）→ (6) 全変異の後に全 PASS を確認
- **変異が実際に当たったかも確認する** — 置換 0 件だと、落ちない理由が「検知できていない」のか「変異が当たっていない」のか区別できない
- **1 件でも変異が素通りしたら、テストの書き方そのものを疑う**（実装の問題ではない）
- **同じ条件を二重に守っているコードは、片方だけの変異では落ちない**。片方を外して PASS だったら**もう片方も外す**。それでも PASS なら本当にテストが無力

## ソース静的検証（ファイルを読んで文字列を検査する形）のアンチパターン

- **`indexOf` の戻り値を検証せず `slice` する** — marker 未検出時に `-1` 起点で末尾から解析され、無言で誤検知する。切り出しヘルパを作り、未検出時は必ず `throw` する
- **インデントを固定した正規表現** — フォーマッタを掛けただけで落ちる。空白・タブのみに絞る（`\s` は改行を含み行境界を跨ぐ）
- **「削除した文字列の不在」を書くと、同じ PR で追加した説明コメントに誤ヒットする** — コード上の出現形（クォート込み等）で絞る
- **ファイル全体に対して「在るか」を見る** — 同じガード文が複数箇所にあると、守りたい 1 箇所を消しても他がヒットして PASS する。**関数単位で切り出して判定する**
- **「呼び出しが在ること」しか検証できない** — 実装を `if (false && guard(...))` に変えても文字列は残るので PASS する。**分岐の中身を守りたいなら純関数へ切り出して振る舞いで固定する**
- **定数を期待値の両辺に使う** — `expect(header).toBe(HEADER.join(","))` は定数を書き換えると期待値も動くため、文言そのものの回帰を検知できない。表示文言はリテラルで pin する別テストを置く
- **否定アサーションは旧実装の形しか捕まえない** — 同じバグを別の書き方で作ると素通りする。肯定（正しい経路を通ること）と対で置き、変異は「呼び出しを外す」と「旧実装へ完全に戻す」の 2 パターン試す

## CI ゲート

**「CI で実行されているか」をテストを追加した本人が確認する。** テストランナーの対象パターンから外れた場所に置くと、テストは書けているのに**無言で 0 実行**になり、ローカルでも CI でも緑に見える。追加したら実行件数を目視する。

**未実行だったテストを初めて CI に載せるときは、TZ・ロケール・ファイルシステム依存が一斉に露出しうる。** CI が UTC で開発機が別 TZ なら、ローカル TZ 基準の assertion はローカルでだけ緑になる。`TZ=UTC` を含む複数 TZ で実測してから載せる。
