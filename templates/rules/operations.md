# 運用・リリースフロー

ブランチ運用・PR 規約・CI/CD の落とし穴。**コードやワークフロー定義から導出しにくいもの**だけを置く。

運用基準は [README.md](./README.md) が SoT。

## Git ワークフロー

- **コミット前に必ずブランチを確認する**（`cd <対象リポ> && git branch --show-current`）。cd を伴わせない確認は無意味（[general.md](./general.md) 参照）
- **ベースブランチ上で直接作業しない。** 作業ブランチを切ってから編集を始める
- **作業開始時に「今いるブランチが基底より遅れていないか」を確認する** — `git rev-list --left-right --count origin/<base>...HEAD` が `10  0` のような形（左 = base が先行 / 右 = 独自コミット 0）なら**マージ済みで放置された古いブランチ**。`git branch --show-current` や `git log -1` では判別できず、そこで作業すると base の更新を巻き戻す差分を作る

## PR

- **PR 本文には `## Affected Surfaces`（影響範囲）と `## Test Plan`（影響範囲 × テストケース対応表）を書く** — レビュアーが「何を見ればよいか」を diff から再構築しなくて済むようにする
- **自分の open PR へ追加 push する前に PR の state を確認する**（`gh pr view <n> --json state --jq .state` が `OPEN`）。マージ済みの head へ push すると、自動削除されたブランチが**「新規ブランチとして復活」**し、修正コミットがどの PR にも乗らない宙吊りになる。復旧は基底起点の新ブランチへ `git cherry-pick` して新 PR + 復活ブランチを削除
- **既存 PR の base を後から付け替えない**（`gh pr edit --base`）。元 base にだけある未マージコミットが全部差分に混入する。新 base 起点で切り直して `git cherry-pick` するのが安全。**例外は新旧 base が完全に同一のとき**（`gh api repos/OWNER/REPO/compare/<old>...<new>` の ahead/behind が 0 なら安全）

## CI

- **CI の失敗が自分の変更起因か既存かは「base と同一コミットの捨てブランチを push して同時間帯で A/B」が決定的** — 再実行は一過性失敗の切り分けには使えるが、同じテストが 3 回連続で落ちたら再実行を重ねても判断がつかない。変更ゼロのブランチを作ると、同じ runner プール・同じ時間帯で base 単体の結果が取れる（判定後は削除する）
- **全体のエラー件数を合否判定に使わない** — base 時点で既存エラーがあるプロジェクトでは、件数では自分の混入を検出できない。**変更ファイル名で grep して、そこに出ないことだけを見る**
